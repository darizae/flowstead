## MVP scope and uniform data contracts

Five **fictional small domestic Florida** Plants are approved for synthetic M1/demo (M0 has three Plants × 48 hours; M1 is implemented and merged). Identical data schema and product features for every Plant, with authorization determining which Plants each operator can access. Every Plant has hourly:
- `influent_flow` — **US gal/h**, mean rate over that hour;
- `rainfall` — **in/h** for hourly interval;
- `dissolved_oxygen` — **mg/L**, one representative hourly sample;
- `effluent_ph` — **unitless**, one representative hourly sample.

Store the unique `(plant_id, timestamp_utc)` hourly key in UTC and render charts in Plant-local IANA timezone with unambiguous DST hour labels. Missing values are **NULL** with quality `missing`, not zeros; `invalid` readings retain their flagged numeric value but are never treated as valid. Preserve synthetic origin, generator version/seed/manifest checksum and source independence; **never import or derive publishable output from DHI WaterBench data or fitted parameters**. Use real map markers with fabricated Plant locations, authorized latest/history views and four correctly labeled charts.

Forecast: for each Plant/issuance, exactly **12 future hourly influent-flow gal/h predictions** with `issued_at`, `target_time`, `predicted_flow`, `model_version`. Start with a baseline such as persistence/seasonal naive, record held-out chronological evaluation, show observed-versus-predicted boundary and meaningful unavailable states. Do not claim real-world predictive accuracy from synthetic tests.

Public demonstration: **all five** validated fictional M1 Plants are owner-approved (2026-11-17) for bounded, anonymous, read-only synthetic Plants/map/history/forecast and permitted on-demand downloads. Apply the server-side public allowlist to exactly those five verified Plant IDs, not user-supplied IDs or private account fields. This is **not** authorization to deploy publicly.

Operators: invite-only Supabase Auth identity; verify JWT and independently enforce per-Plant authorization in FastAPI on **all** Plants lists, map entries, history, forecasts and CSV/PNG/PDF exports. ## D-045 — NATS/JetStream message flow and Alembic migration contract

**Explicit owner decision, 2026-11-17:** the backend MUST use NATS/JetStream for asynchronous, message-driven work and Alembic as its real migration runner. Introduce these as two bounded successor tasks **004a (Alembic baseline)** and **004b (NATS message flow)**, preserving merged tasks 002–004 and immutable M1 data. PostgreSQL is authoritative business storage; JetStream is transport/delivery state. HTTP reads remain FastAPI-to-PostgreSQL with server-side Plant authorization. No new repository or cloud broker is authorized.

**Message semantics.** Use locally health-checked NATS 2 with JetStream in Docker Compose and a vetted compatible Python nats-py dependency pinned in the existing backend lock. Define schema-versioned, typed messages with message ID/correlation ID, Plant ID, source SHA, issued timestamp, and validated provenance; subjects include flowstead.v1.ingest.completed, flowstead.v1.forecast.requested, flowstead.v1.forecast.completed and flowstead.v1.forecast.failed. Separate HTTP request/response from durable asynchronous command processing: an authenticated command/CLI requests forecasting and can return a 202 with correlation/status; GETs query persisted bounded state without writing or blocking on broker availability. Public endpoints remain read-only and may not publish arbitrary Plant commands.

**Consistency.** Persist business changes and a PostgreSQL outbox event together in a transaction. A bounded dispatcher publishes events to JetStream and records confirmed broker acknowledgment. A durable consumer validates version, payload and approved Plant; it deduplicates via a PostgreSQL inbox/unique event ID, calls the existing pure forecast computation, commits exactly twelve future targets plus dedupe receipt before acknowledging. Retry transient errors with backoff, limit delivery attempts, expose dead-letter/terminal error receipts, restart and replay safely. Never use ephemeral pub-sub as the only record of a committed change. The direct local forecast CLI remains as maintenance/backfill; no second forecasting algorithm.

**Actual Alembic adoption.** The backend currently declares alembic but uses a custom backend/migrate.py to run migrations/001_initial.sql and backend/migrations/002_forecast_metadata.sql, tracked in public.schema_migrations. Task 004a must provide a real single-owned Alembic configuration and revision chain. A new database upgraded to head must match the current tables, indexes, constraints and data semantics; an existing verified migrated DB is stamped at its equivalent baseline **without rerunning old DDL or dropping records**. Keep past SQL files and checksum receipts unchanged; future outbox/inbox schema changes use forward Alembic revisions. Add verified root just db-upgrade/db-current commands and real PostgreSQL tests for empty and preexisting DB, repeat upgrade, data survival, and safe local rollback of only new changes. Hosted migrations still require their previously established scoped authorization.

**Indexed test-first strategy** (adapted from integration_tests.zip/docs/SKILL.md). docs/testing/INDEXED_TEST_PLAN.md is the canonical stable-case catalog and docs/testing/TEST_DATA_GUIDE.md defines resource equivalence classes and setup.
